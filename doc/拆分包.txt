0. 文件目的與限制

本文件是交給 Codex／Work／本機開發流程執行的拆分準備包，不代表拆分已完成，也不代表已建立 omniAgent repo、已搬動程式、已修改 migration、已部署或已完成 live integration。

依 janusChatGPT 專案規則，ChatGPT 可以分析目前 GitHub、更新文件、產出 Codex 工作指令、patch 建議與驗收條件，但不得直接修改 Python、TypeScript／JavaScript、Dart、SQL migration、shell／PowerShell、Dockerfile、Cloud Build、GitHub Actions、runtime／deployment config、tests 或 application source。因此本文件刻意不是可直接執行的 .ps1／.sh 搬檔腳本，而是可由 Codex 精確執行的 migration manifest + runbook。

拆分原則：copy-first、boundary-first、acceptance-before-delete。不得先把 Janus 現有可用功能刪掉再補 omniAgent；不得把 partial success 包裝成 full success。

1. 最終責任邊界

1.1 omniAgent 負責
- 通用 Chat UI / Chat API
- Threads / Turns / Items / Sessions / Memory
- Agent Runtime / orchestration
- provider adapters：Gemini、OpenRouter、Codex
- Codex App Server lifecycle / managed auth / device-code / bridge
- generic MCP Host / MCP Client / tool discovery / tool dispatch
- Skills runtime / skill versioning
- Approval / shell / temporary file-operation boundary
- streaming / cursor / reconnect / cancellation / checkpoints
- generic assistant storage
- future LangChain / LangGraph orchestration layer
- 可同時連 Janus、life_assistant 與未來其他 domain systems

1.2 Janus 保留
- 市場資料 ingestion / Stage / Core / Mart
- canonical data、PIT / future leakage、provenance、DQ
- deterministic features / research models
- Intelligence Mart / five-role research pipeline
- Supply-chain Intelligence
- portfolio / trades / journal / notes / watchlist / investment profile
- investment-specific authentication / authorization / ownership
- Janus bounded research/context API
- Janus MCP Adapter / Gateway / OAuth（供 ChatGPT 等外部 consumer 使用）
- publication / governance / audit
- Janus User/Admin UI
- Janus 不保留任何 chat/assistant product surface；所有 conversational / agent UX 歸 omniAgent

核心規則：Domain system 負責「能做什麼」，omniAgent 負責「怎麼思考、怎麼串、先做什麼後做什麼」。Janus 不知道、不依賴 omniAgent 的具體實作；Janus 僅暴露穩定的 authenticated API/MCP capability。

2. 不得破壞的系統邊界

- omniAgent 不得直接 import Janus Python／TypeScript internal packages。
- omniAgent 不得直接連 Janus PostgreSQL、GCS、Iceberg catalog 或知道 Janus table name、GCS URI、object path、credential locator。
- omniAgent 取得 Janus 能力必須透過 authenticated bounded HTTP API 或 MCP。
- Janus 回傳 context 時仍須保留 owner scope、PIT、as-of、provenance、bounded output 與 source authorization。
- Janus canonical numbers / facts 不由 omniAgent LLM 修改。
- ChatGPT Custom MCP App 與 omniAgent 是兩條不同 consumer path；拆 omniAgent 不得破壞既有 Janus MCP connector。
- life_assistant 未來可作為第二個 domain connector，但第一階段不得為了它改壞 Janus。

3. Migration classification

MOVE-CANDIDATE：高信心屬於通用 Agent 平台；目標是搬入 omniAgent，但實際檔案移動由 Codex 執行。
SPLIT-REFACTOR：同一檔案混合 Janus 與 Assistant 邏輯，必須拆，不能整檔搬。
COPY-THEN-REFACTOR：先複製到 omniAgent，建立相容邊界後再決定何時從 Janus 移除舊版本。
KEEP-JANUS：明確屬 Janus domain / data / MCP boundary。
DEFER-REVIEW：涉及 live data、migration history、cloud resource、Secrets、OAuth 或 deployment，先保留，另案 cutover。

7. 驗收條件

Janus acceptance：
- ingestion/Core/Mart/portfolio/journal/watchlist/research 不因拆分 regression。
- Janus MCP connector 仍可獨立被 ChatGPT 使用。
- Janus context API 保有 owner scope、PIT、provenance、sanitization、output bounds。

- 可獨立 build / test / start。
- Gemini/OpenRouter/Codex provider tests 通過。
- Threads/Turns/Events/streaming/cancel/reconnect 可用。
- Approval request/decision 維持 digest、expiry、scope binding。
- MCP discovery/call/timeout/cancel/disconnect 可用。
- 無 Janus DB/GCS/Iceberg direct access。
- 可用 real dev Janus API/MCP 取得投資 context。
- 未來可接 life_assistant，不需 import Janus code。

Integration acceptance：
- 使用真實 dev Janus 做至少一條端到端流程：User → omniAgent → Janus bounded tool/context → model → answer/citation。
- ChatGPT → Janus MCP path 仍獨立正常。
- secret 不進 browser/client/log/thread payload。
- rollback 可以把流量切回拆分前 Janus chat path（在 cleanup 前）。

完成判定：只有 code、tests、CI、deployment、live runtime、real integration evidence 均符合才可稱 split complete。建立 repo 或搬完檔案不算完成。

ARCHIVE-HISTORICAL：已完成且具有歷史價值的 archive 不為了消除字串而改寫歷史，但必須確保 active docs 不再把舊架構當現況。歷史文件若可能誤導，應加 historical / superseded 標記，而不是改寫當時事實。

CROSS-PROJECT-REFERENCE：Janus 與 omniAgent 都只記錄穩定的 wire contract / endpoint / MCP capability / ownership boundary，不互相引用對方 repository internal source path 作為正式架構。

13.3 每一 phase 的文件同步要求

Phase 1 建立 omniAgent skeleton 時：
- 建立 omniAgent README、architecture、migration-from-janus、janus-connector 文件。
- 標示哪些 code 只是 copy-first compatibility，尚未 cutover。
- 不得在 omniAgent 文件宣稱已接管 live runtime，除非 runtime evidence 已存在。

Phase 2 wire boundary 時：
- Janus spec 更新為 domain API/MCP provider。
- omniAgent spec 更新為 external consumer/orchestrator。
- 明確記錄 owner identity、auth boundary、context contract、PIT/provenance、bounded response。

Phase 3 chat/storage ownership 時：
- WBS/todo/runbook 必須同步誰擁有 thread/event/storage/write path。
- 若仍 dual-write / dual-read / compatibility，文件必須明寫，不可簡化成已完成 cutover。

Phase 4 UI extraction 時：
- Janus UI 文件移除 generic provider/runtime/MCP/Skills/approval ownership 描述。
- omniAgent UI 文件新增完整 Chat/Threads/Tools/Approvals/Provider UX。
- Janus UI 文件必須移除 Ask Janus、Chat、assistant、provider/runtime selector 等 conversational product surface；不得保留替代入口。

Phase 5 deployment cutover 時：
- runbook、service naming、health check、OAuth/Secret ownership、Cloud Run routing 與 rollback 全部同步。
- 任何舊 service 名稱若仍暫時保留，必須明確標示 compatibility alias / legacy resource，而不是裝作不存在。

Phase 6 cleanup 時：
- 清除 active docs 中已失效的 Janus internal Agent Gateway / Chat API / generic assistant ownership 敘述。
- 將 migration TODO 關閉前，必須完成 stale-reference scan。

13.4 stale-reference scan 關鍵字

Codex 在每個 phase 結束與最終 cleanup 前，需對 Janus 與 omniAgent 的 active docs 全域搜尋至少以下詞群，逐項判斷是否仍正確，不可機械式全刪：
- agent-gateway / Agent Gateway
- private assistant / 私人助理
- WBS-4C
- Chat API / chats/threads / events
- assistant_storage / private_assistant_storage
- Codex bridge / Codex App Server
- OpenRouter / Gemini provider
- MCP Host / MCP Servers / Tools
- Skills / skill profile
- approval / approval request
- provider / runtime selector
- assistant.v1
- context_sources
- janus-omniforge path references
- services/agent-gateway
- apps/user_app ChatPage
- Cloud Run agent gateway service names
- legacy POC / dev-only / production-only 語意

注意：上述字串出現不代表一定要刪；歷史 migration/archive 可保留舊名稱，Janus MCP connector 也仍會合法包含 MCP。active Janus 架構文件則不得把 omniAgent、Agent Gateway、Chat runtime 描述成 Janus dependency 或內建責任；驗收的是 ownership / current-state 語意正確，而不是零字串命中。

13.5 文件一致性驗收

文件 gate 至少包含：
- Janus README / WBS / spec / todo / UI / runbook 對同一 capability 的 owner 不互相矛盾。
- omniAgent README / architecture / runbook 與實際 repo / runtime evidence 一致。
- active Janus 文件不再把 generic assistant platform 描述成 Janus 長期內建 responsibility，且不得將 omniAgent 描述成 Janus 必要 dependency。
- omniAgent 文件不得宣稱直接讀 Janus DB/GCS/Iceberg/internal packages。
- Janus context/data governance 文件仍保留 canonical data、PIT、future leakage、provenance、source authorization、publication gate 與 LLM 不得改 canonical numbers。
- Janus ChatGPT MCP connector 保持 Janus 自身 external-consumer boundary；omniAgent 僅作為其中一個可能的外部 consumer，不形成 Janus 反向依賴。
- dev = 目前真實使用中的環境；不得因拆分重新引入「dev 只能 mock/POC、未到 prod 不算可用」舊語意。
- archive/history 與 current/active 文件分層清楚。
- 所有 active internal links / file paths / commands / service names 指向實際存在的新位置或明確 compatibility target。
- 文件不能比 implementation 提前宣稱完成；partial / pending / dual-run 狀態要原樣揭露。

13.6 完成定義補強

omniAgent split complete = code ownership + tests + CI + deployment + live integration + documentation ownership + stale-reference scan 全部完成。

若程式已拆，但 active docs 尚有舊 ownership / 舊路徑 / 舊 runtime 語意，狀態必須是 DOCUMENTATION MIGRATION INCOMPLETE，不得標示 split complete。
